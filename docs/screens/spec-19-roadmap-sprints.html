19 — Roadmap & Sprints

Sprint-by-sprint breakdown. MVP first (Sprints 0–5), then Phase 1 full (Sprints 6–18), then Phase 2 (Sprints 19–26), then Phase 3 (Sprints 27–30).

1. Roadmap Overview

Phase Sprints Weeks Outcome
MVP Pilot 0–5 1–12 Pilot live at 1–2 nurseries
Phase 1 Full 6–18 13–38 All 13 modules live, first paid customers
Phase 2 19–26 39–54 Learning & Assessment, mobile maturity
Phase 3 27–30 55–62 Multi-centre, payments, ERP, Open API

Each sprint is 2 weeks. Sprint 0 is the setup sprint. Total Phase 1: 38 weeks (19 sprints).

2. MVP Pilot (Sprints 0–5)

Sprint 0 — Setup & Planning (Weeks 1–2)

Goal: Environment ready, scope locked, pilot nurseries signed.

Deliverables: - [ ] Monorepo scaffolded: backend/ (.NET 8), web/ (Vite+React+TS), mobile/ (Expo+RN+TS), infra/, docs/. - [ ] .cursorrules in place. - [ ] Docker Compose for local dev (PostgreSQL 16, Redis 7, RabbitMQ 3.13, Keycloak 24, MinIO, MailHog). - [ ] CI/CD pipeline skeleton (GitHub Actions): build, test, lint, typecheck on PR. - [ ] Keycloak realm configured for first tenant. - [ ] EF Core initial migration (tenant + app_user + role tables). - [ ] First commit on main. - [ ] Pilot nursery #1 signed (LOI or pilot agreement). - [ ] Pilot nursery #2 in conversation (target: signed by Sprint 2). - [ ] Legal counsel engaged for PDPL review. - [ ] Cloud provider selected (AWS ME Central recommended). - [ ] Tech Lead + Product Owner + 2 backend + 1 frontend + 1 mobile + 1 QA identified.

Exit criteria: - Local dev environment runs (docker compose up + dotnet watch run + pnpm dev all succeed). - CI passes on a "hello world" PR. - Pilot nursery #1 committed.

Files to read first: 00-MASTER-BRIEF.md, 02-PRD-MVP.md, 05-TECH-STACK.md, 11-DEVOPS-INFRASTRUCTURE.md, 18-CURSOR-RULES.md.

Sprint 1 — Centre Management + Auth (Weeks 3–4)

Goal: User can log in, create rooms/students/staff, see them in a list.

Deliverables: - [ ] Keycloak integration in backend (JWT validation, role-based auth). - [ ] Keycloak JS adapter in web frontend. - [ ] Login page + auth flow (login, logout, refresh). - [ ] Role-based access control (5 roles: super_admin, centre_admin, teacher, parent, receptionist). - [ ] Tenant context middleware + RLS setup. - [ ] EF Core entities: Student, Staff, Room, Program, StudentGroup, Label, Guardian, StudentGuardian, AppUser, Role, UserRole. - [ ] EF Core migrations for all entities. - [ ] RLS policies on all tenant tables. - [ ] Audit log interceptor + audit_log table (append-only trigger). - [ ] API endpoints: students CRUD, staff CRUD, rooms CRUD, programs CRUD, groups CRUD, labels CRUD, guardians CRUD. - [ ] Web frontend: login page, dashboard shell, students list + create, rooms list + create, staff list + create. - [ ] i18n setup (EN + AR), language switcher, RTL support. - [ ] shadcn/ui setup with theme (per 14-UX-UI-DESIGN.md). - [ ] Unit tests for all entities + handlers (target 80% coverage). - [ ] Integration tests for all endpoints. - [ ] Parent-child ownership tests (parent A cannot access parent B's child).

Exit criteria: - Centre Admin can log in, create rooms, programs, students, staff, guardians. - Teacher can log in, see rooms they're assigned to. - Parent can log in, see only their children. - All tests pass on CI. - Both LTR and RTL UI tested.

Files to read first: 02-PRD-MVP.md §3.2, 07-DATABASE-SCHEMA.md §2.2, 08-API-SPEC.md §15, 09-AUTH-SECURITY.md, 12-WEB-FRONTEND.md, 14-UX-UI-DESIGN.md.

Sprint 2 — Attendance + Dashboard (Weeks 5–6)

Goal: Staff can check students in/out, see live ratios on dashboard.

Deliverables: - [ ] EF Core entities: AttendanceRecord (partitioned), AttendanceEvent (immutable), LeaveRequest, LeaveType. - [ ] Migrations for attendance entities + monthly partitioning. - [ ] API endpoints: check-in, check-out, mark-absent, attendance list, attendance forecast, monthly report. - [ ] Barcode input handling (HID keyboard emulation on web). - [ ] Mobile camera scanning (react-native-vision-camera + MLKit) — early mobile skeleton. - [ ] SignalR hub setup + Redis backplane. - [ ] Real-time ratio calculation service. - [ ] Ratio breach detection + event publication. - [ ] Dashboard page: KPI cards, attendance summary, live ratio widget, pending actions widget. - [ ] WebSocket-driven dashboard updates (real-time). - [ ] Materialized views: mv_daily_attendance_summary, mv_live_ratio. - [ ] Hangfire setup for background jobs. - [ ] Leave request workflow (create, approve, reject). - [ ] Unit tests + integration tests. - [ ] Performance test: dashboard p95 < 2s (k6 smoke test).

Exit criteria: - Staff can check in/out students via barcode + manual button. - Dashboard shows live ratios, updates in real-time. - Ratio breach triggers Critical notification (push + in-app banner). - Leave request workflow functional.

Files to read first: 02-PRD-MVP.md §3.3, 07-DATABASE-SCHEMA.md §2.3, 08-API-SPEC.md §15.5, 06-ARCHITECTURE.md §4.2 + §5.

Sprint 3 — Parent Communication + Messaging (Weeks 7–8)

Goal: Teachers can post activities, parents see them; staff + parents can message.

Deliverables: - [ ] EF Core entities: Media, ActivityPost, ActivityPostStudent, ActivityPostMedia, DailyReport. - [ ] EF Core entities: MessageThread, Message, MessageReadReceipt, ThreadParticipant. - [ ] Migrations for all entities. - [ ] Presigned URL upload flow (POST /media/presign → client uploads to S3 → POST /activities with media IDs). - [ ] Content moderation pipeline: ClamAV scan + AWS Rekognition (or Azure Content Safety). - [ ] Media Processing module: consumes MediaUploaded events, scans, updates scan_status. - [ ] Activity post creation + approval workflow (PENDING → APPROVED/REJECTED → parent visibility). - [ ] 8 activity types: announcement, photo, video, diary, food, toilet, medical, mood. - [ ] Parent activity feed (chronological, cursor paginated, real-time via SignalR). - [ ] Daily report generation (Hangfire job at 3:30 PM local) + email + push. - [ ] Messaging: shared inbox, threads, read receipts, broadcast. - [ ] Parent messaging UI + staff messaging UI. - [ ] Mobile app skeleton: login, dashboard, attendance scan, activity feed, messaging. - [ ] Unit + integration tests.

Exit criteria: - Teacher can post photo activity, it gets auto-approved after scan, parent sees it. - Parent can message staff, staff see it in shared inbox, staff reply, parent sees reply. - Daily report generated at 3:30 PM, emailed to parent.

Files to read first: 02-PRD-MVP.md §3.4 + §3.5, 07-DATABASE-SCHEMA.md §2.4 + §2.5, 08-API-SPEC.md §15.7 + §15.8.

Sprint 4 — Notifications + Audit + Emergency Reports (Weeks 9–10)

Goal: Notification system live (3 tiers), audit log viewer, emergency reports.

Deliverables: - [ ] EF Core entities: Notification, NotificationDelivery, NotificationPreference, NotificationTemplate. - [ ] Notification module: consumes events from other modules, creates notifications, dispatches to channels. - [ ] 3 tiers: Critical (push + in-app + SMS — but SMS deferred to Sprint 13; Phase 1 MVP uses push + in-app + email fallback), Operational (push + in-app), Informational (email + optional in-app). - [ ] Notification dispatcher (Hangfire job): processes queued deliveries, retries with backoff. - [ ] Critical tier fallback chain (push fail → email). - [ ] FCM integration for push notifications. - [ ] SES integration for transactional email. - [ ] In-app notifications: bell icon, notification center, mark-as-read. - [ ] User notification preferences (Settings → Notifications). - [ ] Audit log viewer (Super Admin): filterable by user, date, entity, action. - [ ] Emergency child report: one-click PDF per student + bulk per room. - [ ] PDF generation via QuestPDF. - [ ] Mobile app: push notification handling, offline emergency report cache (WatermelonDB). - [ ] Unit + integration tests.

Exit criteria: - Ratio breach triggers Critical notification (push + in-app + email if push fails). - Parent receives daily report email. - Super Admin can view audit log + filter. - Emergency report PDF generated in < 2s per student. - Mobile app receives push notifications.

Files to read first: 02-PRD-MVP.md §3.7 + §3.8, 07-DATABASE-SCHEMA.md §2.7 + §2.8, 08-API-SPEC.md §15.10 + §15.12, 15-NOTIFICATIONS.md.

Sprint 5 — Pilot Deployment + UAT + Go-Live (Weeks 11–12)

Goal: MVP deployed to pilot nursery, real users, structured feedback loop.

Deliverables: - [ ] Production infrastructure provisioned (Terraform): EKS, RDS, ElastiCache, Amazon MQ, S3, CloudFront, Route53, KMS, Secrets Manager, WAF. - [ ] Helm charts for nms-api, nms-web, Keycloak. - [ ] CI/CD pipeline complete: PR → dev → staging → production (manual approval). - [ ] Observability: Prometheus, Grafana, Loki, Alertmanager, Sentry (web + mobile). - [ ] Backups: daily RDS snapshot + WAL archiving. - [ ] Staging environment deployed with seed data. - [ ] UAT with internal team (1 week). - [ ] Bug fixes from UAT. - [ ] Pilot nursery #1 onboarding: data migration from existing system, staff training, parent invitations. - [ ] Go-live at pilot nursery #1. - [ ] In-app feedback button. - [ ] Daily check-ins with pilot nursery during week 12. - [ ] Pilot feedback survey sent to staff + parents. - [ ] Pilot retrospective document.

Exit criteria (MVP pilot exit gates, see 02-PRD-MVP.md §4): - Pilot nursery live with ≥10 staff + ≥30 parents active. - ≥80% of expected attendance logged in system. - 0 critical bugs open, ≤3 high bugs open. - Parent portal p95 < 2.5s. - Ratio breach alert delivery < 30s. - Pilot user NPS ≥ 30. - ≥60% of pilot users "would recommend".

Files to read first: 02-PRD-MVP.md §4, 11-DEVOPS-INFRASTRUCTURE.md, 21-DELIVERY-CHECKLIST.md.

6. Sprint Ceremonies

6.1 Sprint Planning (Day 1 of sprint)

  • 2 hours max.
  • Product Owner presents sprint goal + stories.
  • Team estimates stories (Planning Poker or T-shirt sizing).
  • Capacity check (vacations, holidays).
  • Stories assigned to developers.

6.2 Daily Standup (every day, 15 min)

  • What did I do yesterday?
  • What will I do today?
  • What's blocking me?
  • Async option: post in Slack #standup before 10 AM.

6.3 Mid-Sprint Review (Day 7)

  • 1 hour.
  • Demo work-in-progress to Product Owner.
  • Adjust scope if needed (add/remove stories).
  • Identify blockers.

6.4 Sprint Review (Day 10)

  • 1 hour.
  • Demo completed work to stakeholders.
  • Product Owner accepts/rejects stories.
  • Feedback captured for next sprint.

6.5 Sprint Retrospective (Day 10)

  • 1 hour.
  • What went well?
  • What didn't go well?
  • What will we change next sprint?
  • Action items with owners.

7. Estimation Guidelines

Story size Effort Examples
XS < 1 day Bug fix, copy change, small UI tweak
S 1–2 days New endpoint, new component, small feature
M 3–5 days New entity + CRUD + tests, complex UI screen
L 1–1.5 weeks New module (e.g., Tour Management), major feature
XL 2+ weeks Cross-cutting initiative (e.g., payment gateway, multi-centre) — break into multiple sprints

Team velocity: ~30-40 story points per sprint (4-6 developers).

8. Risk Management

8.1 Top Risks Per Phase

MVP risks (Sprints 0–5): - Pilot nursery pulls out (mitigation: 2 candidates lined up). - Arabic RTL breaks in production (mitigation: mandatory RTL QA every sprint). - Content moderation false positives (mitigation: manual override + appeal flow). - Parents don't adopt web app (mitigation: magic-link login, daily report email drives first login). - Pilot scope creep (mitigation: clear MVP scope doc shared with pilot).

Phase 1 risks (Sprints 6–18): - Billing calculation errors (mitigation: extensive unit tests for invoice generation, manual reconciliation in staging). - Mobile app rejection by App Store (mitigation: follow App Store guidelines, provide demo account, prepare for review feedback). - Performance under load (mitigation: k6 load tests every sprint from Sprint 11). - Security vulnerability discovered (mitigation: SAST + SCA + DAST in CI, pen test before go-live).

Phase 2 risks (Sprints 19–26): - EYFS framework complexity (mitigation: domain expert consult, iterative validation with pilot teachers). - AI observation capture accuracy (mitigation: human review always required, AI is assistive only). - Mobile app performance with offline sync (mitigation: thorough testing of conflict resolution).

Phase 3 risks (Sprints 27–30): - Payment gateway integration complexity (mitigation: use gateway's hosted page, not inline; start with sandbox early). - Multi-tenant data leakage at scale (mitigation: rigorous testing of RLS, automated cross-tenant tests in CI). - ERP integration varies per customer (mitigation: adapter pattern, scope per customer).

8.2 Risk Review

Risk register reviewed at sprint planning. New risks added as identified. Risks assigned owners + mitigation plans.
